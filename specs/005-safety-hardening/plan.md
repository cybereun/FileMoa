# 005 안전성·안정성 강화 — 수정 개발 문서

- 대상 버전: 0.1.6 → 0.2.0
- 작성일: 2026-10-10
- 근거: 코드 리뷰(정적 분석). 앱을 실행해 재현한 결과가 아니므로, 각 항목은 "재현 테스트 작성 → 수정" 순서로 진행한다.
- 원칙: 기존 흐름 `분석 → 추천 → 미리보기 → 승인 → 이동 → 기록 → Undo`를 유지하고, 데이터 손실 가능성이 있는 것을 먼저 고친다.

## 2. P0 — 데이터 손실 차단

### A1. 휴지통 이동이 영구 삭제가 되는 문제
- 위치: `src-tauri/src/recycle.rs:47`
- 원인: `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT`. 휴지통 용량 초과 파일, 네트워크·일부 이동식 드라이브 파일은 확인 없이 영구 삭제된다. `fAnyOperationsAborted`도 확인하지 않아 일부 실패가 성공으로 보인다.
- 수정:
  1. 삭제 전 대상별로 "휴지통 사용 가능" 검사: 네트워크 경로(`\\`), 드라이브 타입이 `DRIVE_REMOTE`/`DRIVE_REMOVABLE`, 파일 크기가 휴지통 한도를 넘는 경우는 삭제 목록에서 제외하고 사유를 반환.
  2. `FOF_WANTNUKEWARNING` 플래그를 추가해 영구 삭제로 바뀌는 경우 작업이 실패하도록 한다(조용히 삭제되지 않게).
  3. `fAnyOperationsAborted != 0`이면 오류로 처리. 파일별 결과(성공/실패/제외 사유)를 반환하도록 반환 타입을 `Vec<RecycleOutcome>`로 변경.
  4. UI는 제외된 항목과 사유를 표시하고, 성공한 개수만 "완료"로 표시.
- 완료 조건: 네트워크 경로·용량 초과 대상이 영구 삭제되지 않고 "제외됨"으로 보고된다. 일부 실패 시 성공/실패 개수가 정확하다.
- 테스트: 경로 분류 함수 단위 테스트(네트워크/이동식/일반), 결과 매핑 단위 테스트. 실제 Shell 호출은 수동 시나리오로 검증.

### A2. 실행 기록을 localStorage에 통째로 저장하는 문제
- 위치: `src/App.tsx:615`, `:284`
- 원인: 최대 100개 계획 전체를 `JSON.stringify`로 저장. 약 5MB 한도를 넘으면 `QuotaExceededError`가 `useEffect` 안에서 던져져 화면이 크래시하고 Undo 기록을 잃을 수 있다.
- 수정:
  1. 기록을 앱 데이터 폴더의 파일(`runs/<id>.json`)로 이전(Rust 명령 `list_runs`, `load_run`, `save_run`, `delete_run`). 목록 화면은 요약(id, 시각, 개수, 상태)만 읽고 상세는 필요할 때 읽는다.
  2. 기존 `localStorage['filemoa-runs']`는 첫 실행 시 파일로 이전한 뒤 삭제(1회 마이그레이션). 이전 실패 시 원본을 지우지 않는다.
  3. 남는 `localStorage` 쓰기(설정류)는 전부 try/catch로 감싸는 헬퍼(`writeLocal`)로 교체.
  4. 최상위 에러 바운더리를 추가해 렌더 오류 시 앱 전체가 사라지지 않게 한다.
  5. 30일 보관 정책은 유지하되 백엔드에서 정리.
- 완료 조건: 파일 5만 개짜리 기록을 여러 번 만들어도 앱이 정상 동작한다. 저장소 쓰기 실패가 화면 크래시로 이어지지 않는다.

### A3. 실행 중 중단 시 복구 불가 → 실행 저널
- 위치: `src-tauri/src/planner.rs:798` (`execute_plan`)
- 원인: 모든 이동이 끝난 뒤에야 결과가 반환되고, 기록은 그 후 프런트에서 저장한다. 도중에 앱이 종료되면 이미 이동한 파일의 기록이 없다.
- 수정:
  1. 실행 시작 시 `runs/<id>.json`을 `status: "running"`으로 먼저 저장한다.
  2. 파일 하나를 이동할 때마다 줄 단위 저널(`runs/<id>.journal`, append-only JSON Lines)에 `{index, status, destination}`을 기록하고 일정 간격(예: 50건)마다 flush.
  3. 시작 시 `running` 상태의 기록이 있으면 저널을 합쳐 복구하고, "이전 실행이 중단되었습니다. 지금까지 이동한 N개를 확인/되돌리기" 안내를 표시.
  4. 실행 완료 시 상태를 `completed`로 갱신하고 저널을 병합·삭제.
- 완료 조건: 1만 개 이동 중 프로세스를 강제 종료해도, 재시작 후 이동된 파일 목록이 복구되고 Undo가 가능하다.
- 테스트: 임시 폴더에서 N개 이동 중 중단을 흉내 내는 단위 테스트(저널을 중간까지만 쓴 상태에서 복구 함수 실행).

### A4. 이름 충돌 시 덮어쓰기 위험(TOCTOU)
- 위치: `planner.rs:815`(실행), `:862`(Undo)
- 원인: `exists()` 확인 후 `fs::rename`. Windows에서 Rust의 `rename`은 대상이 있으면 덮어쓴다. 확인과 이동 사이에 파일이 생기면(클라우드 동기화, 다운로드 완료) 데이터가 사라진다.
- 수정:
  1. `MoveFileExW`를 직접 호출하되 `MOVEFILE_REPLACE_EXISTING`을 쓰지 않는다(대상이 있으면 `ERROR_ALREADY_EXISTS`로 실패). `windows-sys`의 `Win32_Storage_FileSystem` 기능을 추가.
  2. 실패 코드가 `ALREADY_EXISTS`이면 `(1)`, `(2)` 번호를 올려 재시도(최대 N회). 비Windows 빌드는 `hard_link + remove` 대체 또는 기존 동작 유지.
  3. 실행·Undo 두 곳 모두 같은 함수(`move_no_replace`)를 사용.
- 완료 조건: 대상이 이미 존재하면 어떤 경우에도 덮어쓰지 않고 번호가 붙는다(Undo는 충돌로 표시).
- 테스트: 대상 선(先)생성 후 이동 시 원본·대상 내용이 모두 보존되는지 확인.

### A5. 클라우드 전용(온라인 전용) 파일 다운로드
- 위치: `planner.rs:892`(`hash_file`), `:615`(경고 문구)
- 원인: 문구는 "다운로드하지 않는다"이지만 해시는 파일 전체를 읽어 OneDrive/Drive의 온라인 전용 파일을 내려받는다.
- 수정:
  1. 파일 속성 `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS(0x400000)`, `FILE_ATTRIBUTE_RECALL_ON_OPEN(0x40000)`, `FILE_ATTRIBUTE_OFFLINE(0x1000)` 검사 함수 `is_cloud_placeholder`.
  2. 중복·대용량 검색에서 해당 파일은 해시하지 않고 "온라인 전용이라 건너뜀" 목록으로 분리 표시. (정리 이동은 이름만 바꾸므로 허용하되 미리보기에 아이콘 표시.)
- 완료 조건: 온라인 전용 파일이 있는 폴더에서 중복 검사를 해도 다운로드가 발생하지 않는다(수동 확인).

## 3. P1 — 백엔드 신뢰 경계

### B1. 실행·Undo가 프런트가 보낸 계획을 그대로 신뢰
- 위치: `lib.rs:90-97`, `planner.rs:798`, `:847`
- 수정:
  1. `plan_organization`이 계획을 서버 쪽(앱 데이터 `plans/<planId>.json`)에 저장하고 `planId`와 함께 반환.
  2. `execute_organization`은 `planId`와 사용자가 제외한 항목 id 목록만 받는다. 파일 경로는 서버에 저장된 계획에서만 읽는다.
  3. AI 제안 적용(`apply_ai_suggestions`)도 서버 계획을 갱신하는 방식으로 변경.
  4. 실행 직전 각 항목을 재검증: 원본이 루트 아래인지, `protected()` 아닌지, 목적지가 같은 루트 아래인지, 원본이 계획 이후 변경되지 않았는지(크기·수정시각).
  5. Undo는 저장된 실행 기록(A2/A3)의 항목만 대상으로 하고 같은 검증을 적용.
- 완료 조건: 조작된 경로를 담은 요청이 거부된다(루트 밖 목적지, 보호 경로, 존재하지 않는 planId).
- 호환: 명령 시그니처가 바뀌므로 `specs/001.../contracts/desktop-commands.md`를 함께 갱신한다.

### B2. 보호 경로 범위 확대
- 위치: `planner.rs:257`(`protected`), `:623`(`create_plan`)
- 수정: 드라이브 루트(`C:\`), 사용자 프로필 루트(`%USERPROFILE%`), `$Recycle.Bin`, `System Volume Information`, `Recovery`, `Windows.old`를 루트 선택 시 거부. 하위 경로 보호는 유지.
- 테스트: 위 경로들이 거부되는 단위 테스트(환경변수 의존 부분은 주입 가능한 형태로 분리).

### B3. 개발 프로젝트 감지 완화·보강
- 위치: `planner.rs:12`(`PROJECT_MARKERS`), `:291`, `:628`
- 문제: 다운로드 폴더에 떨어진 `package.json` 하나로 전체 정리가 거부된다. 반대로 `.sln`, `.csproj`, `pubspec.yaml`, `Makefile`, `.svn`, `.hg`는 감지하지 못한다.
- 수정:
  1. 신호 점수 방식: `.git`/`.hg`/`.svn` 디렉터리는 강한 신호(1개로 프로젝트), 나머지 마커는 약한 신호(같은 폴더에 소스 폴더 `src/`, 잠금 파일, 또는 마커 2개 이상일 때 프로젝트).
  2. 루트 자체가 약한 신호만 가진 경우 거부하지 않고 경고 + 해당 마커 파일만 제외 목록에 넣는다.
  3. 마커 목록에 `.sln`, `.csproj`, `pubspec.yaml`, `Gemfile`, `Makefile`, `deno.json`, `.svn`, `.hg` 추가.
- 완료 조건: Downloads에 `package.json` 단독 파일이 있어도 정리가 가능하고, 실제 프로젝트 폴더는 계속 보호된다.

## 4. P2 — 반응성

### C1. 동기 명령을 비동기로 전환
- 위치: `lib.rs`의 `plan_*`, `execute_*`, `undo_*`, `find_*`
- 원인: `async`가 없는 Tauri 명령은 메인 스레드에서 실행되어 큰 폴더에서 창이 멈춘다.
- 수정: 각 명령을 `async fn` + `tauri::async_runtime::spawn_blocking`으로 바꾼다. 같은 종류 작업은 동시에 하나만 실행(작업 잠금), 중복 호출은 거부.

### C2. 진행률과 취소
- 수정: `tauri::ipc::Channel`로 `{phase, done, total, currentName}` 이벤트를 스트리밍. 취소 토큰(`AtomicBool`)을 공유하고 `cancel_operation` 명령 추가. 스캔·해시·이동 루프에서 토큰을 확인한다. 이동 중 취소는 "현재 파일까지 마치고 중단" 후 기록 유지(A3 저널 덕분에 Undo 가능).
- UI: 진행 바, 현재 파일명, 취소 버튼. `busy` 상태에서 다른 버튼 비활성화.

### C3. 중복 검사 성능
- 수정: 크기 그룹 → 앞 64KB 해시 → 전체 SHA-256 순서로 단계 축소. 크기 그룹별 병렬 해시(스레드 수 제한, 예: 코어 수-1). 프로젝트 폴더(`project()`)와 클라우드 파일(A5)은 제외.
- 완료 조건: 같은 데이터에서 기존 대비 시간이 줄고 결과 집합은 동일.

| E4 | 기본 모델이 오래됨, 모델 목록 미조회 | `ai.rs:167` | 공급자 모델 목록 API로 선택지를 불러오고, 기본값은 설정 파일 상수로 분리. 모델 ID는 문서에 박지 않고 공급자 공식 문서 기준으로 점검 |
| E5 | 파일명에 의한 프롬프트 인젝션 | `ai.rs:523` | 프롬프트에서 파일 목록을 데이터 영역으로 명확히 구분하고, 응답은 id·카테고리 스키마 검증(이미 일부 수행). 새 카테고리는 사용자가 승인한 것만 적용 |
